# Documentation Style Guide

Use this guide when adding or updating NutsNews documentation.

---

## Goals

Good docs should help someone quickly answer:

1. What is this?
2. When should I use it?
3. What do I do next?
4. How do I confirm it worked?
5. Where do I go if it fails?

---

## Structure

Use this order for most docs:

```text
# Clear title

One-sentence summary.

## When to use this
## What it covers
## Required setup
## Steps
## Verify
## Troubleshooting
## Related docs
```

Not every doc needs every section. Keep the useful parts and remove filler.

---

## Wording

Write in plain language.

Prefer:

- “Run this command”
- “Check this dashboard”
- “The Worker saves accepted articles”
- “If this fails, check the logs”

Avoid:

- Long background before the action
- Repeating the same idea in several places
- Dense paragraphs when a table is clearer
- Internal shorthand that future readers may not know

## Dual-audience publishing

Every technical source document must be mirrored for Simple readers in `audiences/simple/`.

When adding or changing docs:

- Preserve one canonical source file under the repo path.
- Keep the matching `audiences/simple/` mirror file aligned in intent.
- Keep diagram paths stable in frontmatter:
  - `wiki.primary_diagram` (or `wiki.primary_diagram.file`) in canonical source files.
  - `diagram` entries are regenerated by tooling and should not be hand-edited in generated output.

Do not diverge `title`, `slug`, `collection`, `section`, `status`, or `order` unless a review requires it.

---

## Links

Reachability starts from [README.md](README.md) and the `updates` / `archive` collections.

When adding a new doc:

1. Add the technical source file at the repository root or logical folder.
2. Add the Simple mirror under `audiences/simple/` at the same relative path.
3. Keep one-off update notes in `updates/` or `archive/`.
4. Add related-doc links at the bottom of the new doc when useful.
5. Use the release/issue naming pattern in `updates/` and `archive/` so links stay discoverable.

---

## Naming

Use clear uppercase file names for long-lived docs:

```text
GOOD: DEPLOYMENT_CHECKLIST.md
GOOD: WEB_OFFLINE_E2E_REGRESSION_TEST.md
GOOD: FREE_TIER_GUARDRAILS.md
```

Use `updates/` and `archive/` directories for temporary implementation notes.

---

## Maintenance Rules

Update docs when a change affects:

- Deployment
- Production operations
- Monitoring
- Database shape
- Worker behavior
- AI provider behavior
- Public user flows
- Admin dashboards
- Regression tests
- Security or dependency routines

Do not leave temporary bundle READMEs in the repository root.
